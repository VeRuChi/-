# Междугороднее автобусное расписание

Тестовое задание: проектирование БД для хранения расписания междугородних автобусов и SQL-запрос для электронного табло.

## Стек

* PostgreSQL 15+
* SQL

## Структура БД

Используются следующие таблицы:

* `cities` — города;
* `bus_stops` — остановки;
* `buses` — автобусы;
* `trips` — рейсы;
* `trip_stops` — остановки конкретного рейса с порядком следования и временем прибытия/отправления.

Связи:

cities
   │
   └── bus_stops
           │
           │
trips ─────┴── trip_stops
  │
  └── buses


## Запуск

Создать базу данных PostgreSQL и выполнить файлы последовательно:


psql -U postgres -d bus_schedule -f sql/schema.sql
psql -U postgres -d bus_schedule -f sql/seed.sql
psql -U postgres -d bus_schedule -f sql/query.sql
psql -U postgres -d bus_schedule -f sql/tests.sql


## Основной запрос

Для электронного табло необходимо получить следующие 15 рейсов с заданной остановки.

Параметр:


:stop_id


Запрос фильтрует только будущие рейсы, сортирует их по времени отправления и возвращает первые 15.

## Индексы

Основной индекс:


CREATE INDEX idx_trip_stops_stop_departure
ON trip_stops (stop_id, departure_at);


Он соответствует условиям:


WHERE stop_id = :stop_id
  AND departure_at >= CURRENT_TIMESTAMP


и сортировке:


ORDER BY departure_at


Благодаря составному индексу PostgreSQL может сразу перейти к нужной остановке и читать записи в порядке времени отправления. В сочетании с `LIMIT 15` это позволяет не сортировать весь набор найденных рейсов.

Дополнительные индексы создаются на внешних ключах, которые используются при JOIN.

## План выполнения

План проверяется следующим запросом:


EXPLAIN (ANALYZE, BUFFERS)
...


При достаточно большом объёме данных ожидается использование:


Index Scan
    ↓
idx_trip_stops_stop_departure
    ↓
JOIN по первичным ключам
    ↓
LIMIT 15


Конкретный план зависит от статистики таблиц, количества данных и настроек PostgreSQL, поэтому фактический результат необходимо проверять через `EXPLAIN ANALYZE`.

При проверке плана обращаю внимание на:

* используется ли `idx_trip_stops_stop_departure`;
* отсутствует ли дорогостоящая сортировка большого набора данных;
* количество `actual rows`;
* `Buffers`;
* соответствие `estimated rows` и `actual rows`;
* фактическое время выполнения.

## Почему не используется отдельный индекс по `stop_id`

Индекс:


(stop_id, departure_at)


уже позволяет выполнять поиск по `stop_id`, поскольку он является первой колонкой составного индекса.

Поэтому отдельный индекс:


(stop_id)


для основного запроса не требуется.

## Ограничения модели

В рамках тестового задания каждый рейс представлен отдельной записью в `trips`, а его остановки — в `trip_stops`.

Такую модель можно расширить для промышленной системы, например выделив шаблон маршрута и регулярное расписание отдельно от фактических отправлений.
